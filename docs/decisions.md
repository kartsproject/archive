## 2. 사이트 구조

| 항목 | 결정 | 이유 |
|---|---|---|
| 탐색 방식 | 목록 나열이 아니라 **실제 일정표를 화면에 옮기고, 시간대를 고르면 그때 생산된 자료가 열리는 구조** | 이용자는 "며칠 몇 시에 어떤 수업이었는지"를 이미 알고 있는 경우가 대부분 |
| 메뉴 방식 | 메뉴형이 아닌 **단계형 화면 + 상시 검색** | 단계마다 범위가 좁혀져 자료를 찾는 경로가 하나로 유지됨 |
| 흐름 | 로그인 → 분야 → 프로그램 → 일정표 → 목록·열람 (2026-10-07 변경: 목록과 열람을 한 화면으로 합침. 처음에는 목록 → 열람의 6단계) | 위와 같음 |
| 자료 목록을 보여 주는 이유 | 한 시간대에 자료가 여러 건인 경우가 일반적(카메라 복수 운용, 녹화 분할, 사진 다수). **2026-10-07 변경**: 일정표 칸을 누르면 목록 카드 화면을 거치지 않고, 가운데 재생·확대 칸 + 오른쪽 영상·사진 목록을 한 화면에 바로 펼친다(사용자 결정) | 시간대에서 영상 하나로만 가면 나머지 자료가 묻히는데, 오른쪽 목록이 늘 보이므로 묻히지 않으면서 클릭 한 번이 줄어듦 |
| 공통 상단바 | 로고 · 경로 표시 · 통합검색 · 로그아웃 | 어느 단계에서도 검색과 이탈이 가능해야 함 |
| 프로그램 선택 | 워크숍 · 심화 멘토링 · 겨울 심화캠프 (3개) | 학생 작품은 시간대에 귀속되지 않아 별도 카드(4번째 프로그램)로 넣었었으나, 검색 → 인물 상세를 통해서만 접근하는 쪽으로 되돌림(2026-09-17) |
| 귀속 기준 | 워크숍 = 일자 × 시간대 / 멘토링 = 분야 × 권역 × 회차 / 캠프 = 일자 | 프로그램마다 일정이 짜이는 단위가 다름 |
| 학생 작품 | 학생 · 분야 단위로 관리하되 별도 화면 진입점은 없음(검색으로만 노출) | 위와 같음 |
| 라우팅 | 해시 라우팅 (`#/music/workshop/세션ID`) | 새로고침 없이 이동하고, 링크 공유가 가능함 |
| 데이터 로딩 | 인증 직후 공개 자료를 한 번에 받고, 이후 화면 이동·검색은 브라우저에서 처리 | 요청 수를 줄여 Apps Script 실행 한도를 아낌 |
| 응답 캐시 | 관문이 「접근코드」·「설정」과 data 응답을 CacheService에 담아 두고, 시트 편집 트리거가 캐시 버전을 올려 무효화 (2026-09-21) | 시트 4개를 여는 데만 수 초가 걸려 매 요청마다 읽을 이유가 없음. 무효화를 키 삭제가 아니라 버전 올리기로 한 것은 동시 요청과 어긋나지 않게 하기 위함. 스크립트가 쓴 값에는 편집 트리거가 반응하지 않아 메뉴 작업 끝에서 직접 무효화하고, 수동 [캐시 비우기] 메뉴도 둠 |
| 접속 기록 | 실패 기록은 즉시, 성공 기록은 모았다가 1분 트리거가 한꺼번에 기록 (2026-09-21) | 시트 쓰기가 로그인 응답 시간에 그대로 더해짐. 침입 시도의 근거가 되는 실패 기록만 지연 없이 남기고, 성공 기록은 미뤄도 감사에 지장이 없다고 판단 |
| 예비 요청 | 화면이 3초 안에 응답을 못 받으면 같은 요청을 한 번 더 보내고 먼저 온 응답을 사용. auth는 `requestId`로 관문이 중복을 거름 (2026-09-21) | Apps Script 입구 대기가 요청마다 무작위로 걸려, 다시 보내면 대개 바로 옴. 중복을 거르지 않으면 토큰·로그가 두 번 생김 |
| 새로고침 | 자료를 기다리지 않고 곧바로 화면에 들어간 뒤 뒤에서 받음(로그인과 동일). 별도 로딩 화면 제거 (2026-09-21) | 새로고침만 data 응답을 기다려 15초 제한에 걸리는 경우가 많았음 |
| 사진 미리 받기 | 자료 페이지에 들어가면 화면을 먼저 보여 주고, 뒤에서 `photos` 요청 한 번으로 그 수업의 사진을 받아 메모리에 보관. 1MB 이상 사진과 합계 4MB를 넘는 사진은 빼고 클릭 시 `photo`로 받음. 보관함 상한 약 30MB, 로그아웃 시 비움. 인물 상세는 미리 받지 않음. `photos`는 예비 요청을 쓰지 않음 (2026-09-30, `docs/api.md` 3-5) | 사진 지연의 대부분은 크기가 아니라 요청 한 번의 왕복 비용(109KB 사진도 약 3초)이라, 요청 횟수를 수업당 1번으로 줄여야 효과가 있음. 동시에 여러 장을 요청하면 관문이 배포자 계정 하나의 동시 실행 한도를 나눠 써 다른 사람의 로그인까지 밀릴 수 있음. 적용 후 머문 뒤 클릭 0.1초, 들어오자마자 클릭 약 3초(묶음 대기) |
| auth와 data 분리 | 로그인(auth) 응답에 자료를 담지 않고, 화면은 auth 응답만 받으면 바로 진입한 뒤 data를 뒤에서 받음 | 자료를 로그인 응답에 함께 담았을 때 로그인 대기가 너무 길어 분리함. 합치면 로그인도 data 전체를 기다리게 됨 |
| 기존 자산 | 기존 워크숍 영상 아카이브 화면을 **재활용**하되, 데이터와 로그인 방식은 가져오지 않음 | 일정표 격자·한글 입력 보정 등은 그대로 쓸 값어치가 있으나, 기존 접근코드 검증은 브라우저에서만 이뤄져 새 설계와 맞지 않음 |

## 3. 화면 규칙

| 항목 | 규칙 |
|---|---|
| 흐름 | 로그인 → 분야 → 프로그램 → 일정표 → 목록·열람 (한 화면, 2026-10-07) |
| 프로그램 | 워크숍 · 멘토링 · 캠프 (학생 작품은 검색으로만 접근) |
| 첫 화면 | 분야 코드 → 해당 분야 / STAFF → 분야 선택 |
| 일정표 | 워크숍 격자(실제 일정표 그대로, 2026-10-08) · 멘토링 격자 · 캠프 카드, 자료 없는 칸은 흐리게·누를 수 없음 |
| 검색 | 분야 · 활동명 · 수업명 · 교강사 · 학생 · 장소 |
| 로그인 유지 | 새로고침 유지 / 탭 닫으면 해제 |
| 금지 | 워터마크 표시, 영상 내려받기, 검색엔진 노출 |

**보충**

| 항목 | 결정 | 이유 |
|---|---|---|
| 분야 이동 | 코드에 따라 첫 화면만 다르고, 다른 분야로의 이동은 제한하지 않음 | 교강사가 타 분야 교수법을 참고하는 것이 이 사이트의 주요 이용 목적 중 하나임 |
| 일정표 표시 | 자료 보유 칸을 강조해 미보유 칸과 구분. 미보유 칸은 흐리게 두고 누를 수 없음 (2026-10-08, 부실장님 피드백 — 09-18의 "항상 클릭 가능"에서 변경) | 빈 칸을 눌러보는 헛걸음을 줄임. 실제 일정표로 바꾸면서 점심·등록처럼 영상이 생길 수 없는 칸이 생김 |
| 자료 목록 | 영상 · 사진 · 작품 탭으로 구분. 수업 화면에서는 오른쪽 목록 위의 탭으로, 한 종류뿐이면 탭 없이 「영상 목록 (N)」 제목만 (2026-10-07) | 유형별로 보는 방식이 달라 섞이면 찾기 어려움 |
| 열람 | 영상은 화면 안 재생, 사진·작품은 확대 보기, 참여자 칩 → 인물 상세 이동 | 영상이 사이트 밖에서 열리면 도메인 제한이 무력해짐 |
| 빈 프로그램 카드 | 그 분야에 「일정」이 없는 프로그램은 프로그램 선택 화면에서 「준비중」으로 막음. 일정이 들어오면 자동으로 열림 (2026-10-07, 차장님 요청) | 멘토링·캠프는 아직 자료가 없어 들어가도 빈 일정표뿐임. 고정으로 막지 않고 시트 기준으로 정해, 자료가 들어올 때 코드를 고칠 필요가 없게 함 |
| 영상 제목 | 수업 화면의 가운데 제목은 수업명(여럿이면 「수업명 · 영상 N」), 파일명은 아래 작게 (2026-10-07, 사용자 결정) | 파일명(`26-ws-music-0807-1000-1_01.mp4`)은 이용자가 읽기 어려움. 파일명은 원본 찾기표에서 하드 원본을 찾는 열쇠라 남김 |
| 시각 링크 | 「현재 시각 링크 복사」 버튼으로 `#/분야/프로그램/세션ID?v=영상 순번&t=초` 주소를 복사. 받은 사람은 로그인 후 그 영상을 그 시각에 맞춰 봄 (2026-10-07, 차장님 요청) | Vimeo 자체 공유는 vimeo.com 주소라 숨김·도메인 제한 영상이 열리지 않음. 영상 위 오른쪽 클릭 메뉴는 Vimeo 화면(다른 도메인) 안이라 사이트가 가로챌 수 없어 별도 버튼으로 둠. 링크에 토큰을 넣지 않으므로 접근코드 없이는 열리지 않음 |
| 검색 결과 | 사람 · 수업 · 작품으로 구분. 인물 상세에 참여 이력과 함께 참여한 인물 | 한 번의 입력으로 전 항목을 조회하되 결과 성격이 섞이지 않게 함 |
| 인물 상세 | 그 학생이 참여한 클래스 영상 + 만든 작품을 함께 표시 | 2026-09-17 결정 |
| 동명이인 검색 | 학생ID(5절)로 구분되는 동명이인이 있으면 목록으로 보여주고 선택하게 함 | 성명만으로는 검색 결과가 서로 다른 학생을 합칠 수 있음 |
| 성명 검색 | 접근코드 인증자에게만 제공. 홍보 사이트에는 어떤 형태로도 제공하지 않음 | 학생 성명이 외부에 노출되면 안 됨 |
| 진입 화면 안내 | 자료의 외부 유출·재배포 금지를 명시 | 기술적 차단이 닿지 않는 부분을 안내로 보완 |

## 4. 시스템 구성

| 영역 | 결정 | 이유 |
|---|---|---|
| 열람 화면 | HTML · CSS · 바닐라 JS, GitHub Pages (HTTPS 강제) | 무료이고 주소가 고정됨 |
| 배포 방식 | **GitHub Actions(`.github/workflows/pages.yml`)로 `site/` 폴더만 게시** — `main`에 올라오면 자동 게시 (2026-10-30, 저장소를 `kartsproject/archive`로 옮기며 변경). 이전에는 Pages "브랜치에서 배포"(`main` 루트) + 루트 `_config.yml`의 `exclude`였음(2026-09-18) | 루트의 기존 워크숍 아카이브 파일(학생 실명·평문 코드 포함)을 게시에서 내리기 위함. 주소는 `kartsproject.github.io/archive/`(열람), `…/archive/admin.html`(관리자). 예전 `kartsgifted.github.io/archive/site/` 주소는 쓰지 않음 |
| 관문 | **Apps Script 웹앱** (JSON만 응답) | 서버가 없고, 계정 이관만으로 인수인계가 끝남. FastAPI·Spring은 서버 비용과 인수인계 부담으로 미채택 |
| 데이터 | **Google Sheets** (공유 안 함) | 데이터 규모가 작고 비개발자가 직접 관리함. Cloud SQL 등은 상시 비용·인수인계 부담으로 미채택 |
| 영상 | **Vimeo** (1080p 압축본, 비공개, 도메인 제한, 내려받기 차단) | 간편함과 인수인계를 우선함. Bunny Stream은 대안(더 저렴, 토큰 인증 가능) |
| 사진 | Google Drive (공유 안 함). 대표 사진은 관문을 거쳐 축소본으로 전달 | 사진 주소가 유출돼도 열리지 않게 함 |
| 대표 사진 수량 | 한 수업당 5~8장만 화면에 직접 표시, 전체는 폴더로 연결 | 사진 전량 등록 시 워크숍 1회차당 수백 건이 발생해 입력이 불가능함. 대표 사진 선별은 홍보용으로도 필요한 작업이라 결과물을 공유해 중복 작업을 막음 |
| 원본 영상 | 외장 저장장치 2개에 이중 보관, 사이트와 연결하지 않음 | 8TB 규모를 온라인에 둘 이유가 없음 |
| 교체 가능성 | 관문 응답 형식 `{ok, error, data}` 고정, 영상 서비스는 설정값으로 선택 | 나중에 관문·영상 서비스만 갈아끼울 수 있게 함 |
| 백엔드 개발 도구 | **clasp**(Google 공식 CLI) 도입 | `apps-script/`를 VSCode에서 작성해 Apps Script 프로젝트로 동기화(push)·배포하기 위함. 웹 편집기에 수동으로 옮기는 방식은 파일이 늘수록 누락·구버전 반영 위험이 커짐 |
| 웹앱 실행 설정 위치 | `appsscript.json`의 `webapp` 필드에 명시(`executeAs: USER_DEPLOYING`, `access: ANYONE_ANONYMOUS`) | 이 설정이 매니페스트에 없으면 `clasp deploy`로 기존 배포에 새 버전을 올릴 때마다 웹앱 접근 설정이 풀려 관문이 404로 막힘(2026-09-17 실제로 겪음). 코드로 고정해두면 재발하지 않음 |

## 5. 시트 구성 (공통 1 + 프로그램별 3)

| 시트 | 탭 | 비고 |
|---|---|---|
| 공통 | 읽어보기 · 학생 · 접근코드 · 설정 · 로그 | 관문 스크립트가 붙는 시트. 메뉴도 여기에만 뜸 |
| 워크숍 | 읽어보기 · 일정 · 자료 · 출석부 · 참여자 | 세 프로그램 시트는 탭·열 구성이 같음 |
| 심화 멘토링 | 위와 같음 | |
| 겨울 심화캠프 | 위와 같음 | |

| 탭 | 입력 | 비고 |
|---|---|---|
| 읽어보기 | 안내 | 입력 규칙과 자료 유형 설명 |
| 일정 | 직접 | 세션ID 자동 생성. 프로그램 열 없음(시트가 프로그램을 정함) |
| 자료 | 직접 | **공개여부** 열: 검수대기(기본값) / 공개 / 비공개 |
| 출석부 | 직접 | 가로 수업 × 세로 성명. 동명이인은 학생ID도 기재 |
| 학생 | 직접 | 학생ID·성명 명부. 동명이인이 실제로 발견된 학생만 등록 |
| 참여자 | 자동 | 같은 시트의 출석부에서 변환 |
| 코드 | 직접 | **버전** 열 있음 (올리면 해당 코드의 모든 접속이 즉시 해제됨) |
| 설정 | 직접 | 사업연도, 영상 서비스, 안내 문구 등 |
| 로그 | 자동 | 일시 · 결과 · 코드 · 이름 · 기기ID · 요청 · 대상 자료 |

| 항목 | 결정 | 이유 |
|---|---|---|
| 프로그램별 시트 분리 | 한 시트(9개 탭)를 **공통 시트 + 프로그램 시트 3개**로 나눔. 학생·코드·설정·로그는 공통, 일정·자료·출석부·참여자는 프로그램별 (2026-09-18) | 한 탭에 모든 프로그램·회차가 섞이면 입력·검수가 어렵고, 특히 출석부 변환이 「참여자」 전체를 다시 쓰는 방식이라 한 프로그램 출석부만 반영하면 다른 프로그램 참여자가 지워짐. 학생ID·접근코드는 프로그램과 무관하게 하나여야 해서 공통에 남김. 실제 자료가 0건인 음악 시범 입력(4.4) 전에 나눠 옮길 데이터가 없음 |
| 프로그램 구분 방식 | 행에 프로그램 열을 두지 않고 **시트로 구분**. 관문이 읽은 시트에 따라 응답의 `program`을 채움 | 열을 두면 시트와 다른 값이 적히는 실수가 생김. 응답 모양이 그대로라 화면 코드를 고치지 않음 |
| 메뉴 위치 | **공통 시트에만** 두고 프로그램을 골라 실행 | 시트 메뉴는 스크립트가 붙은 시트에만 뜸. 프로그램 시트마다 붙이면 Apps Script 프로젝트가 4개가 되어 배포·인수인계 부담이 커짐. 불편이 크면 재검토 |
| 시트 ID 보관 | 프로그램 시트 ID는 Script Properties에만 둠 | 보안 원칙(시트 ID를 파일에 쓰지 않음) 유지 |
| 세션ID 형식 | `{사업연도 2자리}-{프로그램코드}-{분야코드}-{MMDD}-{HHMM}-{순번}` (예: `26-ws-art-0722-1000-1`). **세 프로그램 모두 같은 형식.** HHMM은 「일정」의 시작시각, 순번은 같은 분야·같은 날짜·같은 시작시각 안에서만 1부터 매김. 사업연도는 「설정」 탭 값 (2026-09-18 → 2026-10-02 개정, `apps-script/SessionId.js` 수정은 **구현 대기**) | 연도가 없으면 다음 해 같은 날짜에서 ID가 겹침. 겨울캠프는 이듬해 1월이라 달력 연도가 아니라 사업연도를 씀. 프로그램코드로 ID만 보고도 소속 시트를 알 수 있음. 같은 시간에 여러 수업이 열린다는 차장님 확인(2026-09-30)으로 시작시각과 그 안의 순번을 넣음 — 시각을 HH만 쓰면 10:30 수업을 구분하지 못해 HHMM. 개정 전 멘토링 형식(`26-mt-music-광주-1`)은 같은 분야·권역·회차에 수업이 둘이면 ID가 겹치고 파일명에 한글이 들어가 함께 통일함. 권역·회차는 「일정」 칸에 그대로 있어 멘토링 격자 화면은 영향 없음 |
| 운영 방식 | 행 추가 → [점검] → 검수 후 공개여부 "공개" (버튼 없이 즉시 반영, `data` 요청이 시트를 캐시 없이 바로 읽음) | 담당자가 행만 추가하면 화면이 갱신되게 함 |
| 세션ID 자동 생성 | 분야·일자·시간대를 넣으면 식별자를 자동 부여 | 수기 입력 시 오타 한 글자로 영상이 연결되지 않음 |
| 출석부 자동 변환 | 기존 출석부 형태 그대로 입력하면 참여자 목록으로 변환 | 한 줄씩 입력하면 한 분야만으로도 수백 행이 됨 |
| 영상 파일 이름 | `{세션ID}_{영상번호 2자리}` + 원래 확장자 (예: `26-ws-art-0722-1000-1_01.MP4`). 같은 수업의 파일이 여럿이면(카메라 여러 대, AVCHD 조각) `_01`, `_02`…로 이어 붙이고, 순서는 카메라 폴더 순 → 조각 순. 「자료」의 「파일명」과 같게 쓰고, 「세션ID」 칸에는 `_` 앞부분을 적음 (2026-10-02). 이 이름은 외장 하드 원본이 아니라 **Vimeo에 올리는 압축본**에 붙인다(9절, 2026-10-06) | 이름만 보고 세션ID를 알 수 있어 [영상 매칭]을 `_` 앞부분을 읽는 규칙으로 단순화할 수 있음. 영문·숫자·`-`·`_`만 써서 어느 운영체제·Vimeo에서도 깨지지 않고, 학생 이름 등 개인정보가 들어가지 않음. 영상번호는 수업 단위로 매기고 카메라는 구분하지 않음(차장님 확인 2026-09-30) |
| 원본 영상 수정 범위 | 외장 하드의 원본은 합치기·자르기 등 내용 수정을 하지 않음 (차장님 2026-10-02). 2026-10-06부터는 **이름도 바꾸지 않고 읽기만 함**(9절) | 촬영 쪽 원본이므로. 그래서 AVCHD 조각은 조각마다 영상번호를 붙이고, 통녹화는 자르지 않고 아래 규칙으로 처리 |
| 여러 수업에 걸친 통녹화 | 파일 이름은 녹화가 **시작된(처음 나오는) 수업**의 세션ID로 붙임. 「자료」에는 걸친 수업마다 같은 링크로 한 줄씩 등록하고, 걸친 수업 목록은 영상 지도 엑셀에 기록 (2026-10-02) | 이름 형식을 하나로 유지해 `_` 앞부분이 늘 세션ID 하나가 되게 함(범위를 이름에 넣으면 예외 처리가 생김). 같은 링크를 여러 줄에 등록하면 코드 수정 없이 각 수업 화면에 나옴. 시작 수업은 카메라 시계가 틀린 경우가 많아 폴더 이름과 일정표로 사람이 판단 |
| 학생 단위 영상 이름 | `{사업연도}-{프로그램코드}-{분야코드}-work-{MMDD}-{순번 3자리}` (예: `26-ws-music-work-0807-001.mp4`). 학생 이름은 파일명에 넣지 않고 「자료」의 「학생명」(동명이인이면 「학생ID」도)에 적음. 자료유형은 「작품(영상)」 (2026-10-02). 순번은 같은 날짜 안에서 악기 구분 없이 **학생 이름 가나다순**, 한 학생의 영상이 여럿이면(이름1·이름2) 이어서 매김 (사용자 결정 2026-10-06) | 학생별로 잘라 낸 편집본(스케일 테스트 등)은 수업이 아니라 학생 단위 영상이라 세션ID를 붙일 수 없음. 인물 상세 화면은 「학생명」으로 학생별 영상을 모으므로 파일명에 이름이 없어도 찾을 수 있음 |
| 영상 자동 매칭 | 개정 전 규칙(`20261015_1330_음악_A.mp4`)은 폐기. [영상 매칭]을 새 이름의 `_` 앞부분을 「세션ID」로 옮겨 적는 기능으로 바꿀지 **구현 대기** (`apps-script/VideoMatch.js`) | 기촬영분은 카메라 기본 이름(C0001.MP4 등)이고 카메라 시계도 틀린 경우가 많아 옛 규칙을 쓸 수 없음(2026-10-02 외장 하드 조사) |
| 입력 오류 방지 | 고정값 항목에 선택 목록(드롭다운) 적용 | 표기가 흔들리면 화면에서 묶이지 않음 |
| 보호 | 자동 생성 열과 참여자·로그 탭 잠금 | 자동 계산 값을 사람이 덮어쓰지 못하게 함 |
| 입력 부담 경감이 필요한 이유 | 반복 작업이 **7개월간** 지속됨 | — |
| 동명이인 구분 | 「학생」 탭에 학생ID(수기 순번, `ST-0001`)를 부여해 「참여자」·「자료」 탭에서 성명 대신 대조 | 성명만으로는 동일 인물 여부를 구분할 수 없어, 검색·인물 상세가 서로 다른 학생의 이력을 하나로 합칠 위험이 있음. 발견 빈도가 낮아 자동 생성 없이 수기로 운영 |
| 학생ID 형식 | 의미 없는 순번만 사용. 생년월일 등 개인정보를 형식에 담지 않음 | 생년월일은 성명보다 민감한 개인정보라 식별자 형태로 노출·유통되는 걸 피함. 구분이 목적이면 순번으로 충분함 |

자세한 열 구성은 `docs/sheet-schema.md` 참조.

### 6-1. 접근 통제 (1단계 적용, 워터마크 제외)

| 항목 | 결정 | 이유 |
|---|---|---|
| 구글 로그인 | **사용 안 함** | 계정마다 권한을 부여하는 운영 부담이 큼 |
| 코드 형식 | **`KA-MUSIC-7Q4F`** — 앞부분은 배포 단위, 뒤 4자리 무작위 | 유출 시 어느 경로인지 좁힐 수 있고, 해당 분야만 교체 가능함 |
| 코드 수 | 5개 (운영진 1 + 분야별 4: 음악·무용·전통예술·미술) | 배포·회수 단위를 구분하기 위함 |
| 열람 범위 | **모든 코드가 전체 자료 열람** | 교강사가 타 분야 교수법을 참고하는 것이 주요 이용 목적임 |
| 코드 사용기한 | 운영진 2027-03-31 / 분야별 교강사 2027-02-28 | 사업 기간에 맞춤 |
| 이름 입력 | 코드와 함께 입력, 로그에 기록 | 사후 추적용 |

| 인증 유지 | 토큰을 **sessionStorage**에 보관. 새로고침·외부 사이트 복귀 시 유지, 탭·브라우저 종료 또는 새 탭에서는 재입력 | 공용 PC에서 탭만 닫아도 세션이 끊기게 함 |
| 장기 토큰 | 7일 장기 토큰은 **사용 안 함** | 위와 같음 |

| 기기ID | localStorage의 무작위 값 (인증 수단 아님, 실패 제한·로그 구분용) | 인증에 쓰면 조작 가능함 |
| 워터마크 | **표시하지 않음** | 1단계 범위에서 제외 |

### 6-2. 실제 보호 장치

접근코드는 이용 편의를 위한 장치이며, 실제 보호는 아래 세 가지로 이중 구성한다.

1. **시트 비공개** — 관문을 거치지 않으면 자료에 접근할 수 없음
2. **영상 도메인 제한** — 본 사이트 외에서는 재생되지 않음
3. **검색엔진 색인 차단** — 사이트 주소가 검색 결과에 노출되지 않음

### 6-3. 원칙과 대응

| 항목 | 결정 | 이유 |
|---|---|---|
| 화면 코드 | 데이터·비밀값·권한 판단을 두지 않음 | 화면 코드는 공개·조작되어도 본인 브라우저에만 영향. 관문 주소는 노출을 전제로 함 |

| 그 외 | CSP 메타로 연결 대상 제한, noindex · robots.txt | — |
| 저장소 | GitHub 2단계 인증 · 브랜치 보호 · 외부 라이브러리 최소화 | — |
